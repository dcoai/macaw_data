# Changelog

## Unreleased

The next release is **0.16.0**: it adds public API.

### Changes

- **New: `Macaw.Data.Native.enter/1` is documented, the public entry for a host's own counted process** (#224, #237, spec/04 §1.7). Since 0.14.0 `Native.elixir/1` and `normal_schedulers/1` run their function in a process of their own, so a host that counts reductions in a spawned process, as visualize's `Visualize.Work.reductions/2` does, enters the scope in that process instead. `enter(scope)` puts the flags of `scope`, and whichever of the two the process already holds, in the calling process for the rest of its life: it is only for a process that ends with the scope, and `scope/2` is the scope for any other caller, since nothing clears the flag. It now refuses a scope outside `:elixir | :normal_schedulers` with a `FunctionClauseError`, as `scope/2` does; `enter(:bogus)` put `{nil, true}` in the caller's dictionary and answered `:ok`, so a typo counted on the wrong path with no sign.

## v0.15.0 (2026-11-10)

**A ceiling that refuses a budget it can't use, many rows of a table read by index in one gather, and a push drain that reads each incoming row once** (#199, #205, #215). A budget that is no positive integer is now refused, which is breaking, and there is new public API, so this is a minor.

### Upgrading from 0.14.x

- **Breaking: `Macaw.Data.Source.Finish.ceiling/2` refuses a budget that is neither `nil` nor a positive integer:** `{:error, [{[:budget], {:type, :pos_integer}}]}`, answered with any `host:` and `page:` faults, the budget's first, and `ceiling!/2` raises it. `ceiling(0, host: 10)` was `{:ok, {0, false}}`, and an atom budget read as the ceiling itself. A caller that hands it a budget it has not judged judges it first, or reads the fault; a budget from `Macaw.Data.Source.Request.new/1` is already judged, so a request's budget never meets it.
- **New: `Macaw.Data.Table.rows_at/2` and `rows_at!/2`** read the rows at many indexes in one gather, in the order given, each the row `Macaw.Data.Table.row/2` answers. Use it in place of `row/2` in a loop: over a `:term` column `row/2` reads from its chunk's start, so a loop of it is quadratic in the chunk's rows.
- **`Macaw.Data.Source.Push.drain/2` answers what it answered,** chunk for chunk and digest for digest, and costs less: a 1,000-row increment into a nearly full open chunk 439,545 → 243,533 reductions, and the first drain after a snapshot 785,932 → 591,168. No call changes; the table is below.
- `ci/raises.exs` is the family's current copy (#223). Nothing in the package changes.

### Changes

- **A push drain reads each incoming row once** (#215, #228, #229, spec/01 §1.1.4, §4). `Macaw.Data.Table.apply/2`'s insertions built each row's slot as a `DateTime` to group it, read its instant again to sort it, and matched every key of every row against every column. Now each row's window value is read once, from the increment's packed window column where packing has computed it. Its slot key stands for its slot exactly: a `DateTime` and a naive time at one instant are still two slots, so no chunk id or digest moves. Each slot's term is built once, from one of its rows, and an increment's keys are matched to the header once. Every chunk, fault and count is the one the earlier code gives, which byte-equality properties against a frozen copy of it hold over mixed kinds of time and number, rows into settled slots, and keys spelled as strings, atoms or neither. A 1,000-row drain on the live loop's holding, kernels loaded, median of 21 runs (load 2.8 before, 6.6 after):

  | Drain | Before | After |
  |---|---|---|
  | open chunk nearly empty | 402,655 r, 5.9 ms | 206,643 r, 2.6 ms |
  | open chunk nearly full | 439,545 r, 4.8 ms | 243,533 r, 2.6 ms |
  | first after the snapshot | 785,932 r, 10.5 ms | 591,168 r, 8.2 ms |
  | late, from 500 s before the open chunk's last row | 611,563 r, 7.2 ms | 351,539 r, 4.3 ms |

  Slotting and sorting fell by about 112,000 reductions, matching keys to the header once by about 44,000, and reading positions from the packed column by about 40,000 more.
- **New: `Macaw.Data.Table.rows_at/2` and `rows_at!/2` read many rows by index in one gather** (#205, #226, spec/01 §1.1). `{:ok, rows}` in the order given, repeats kept, each row the one `Macaw.Data.Table.row/2` answers and `nil` past the end; an index that is no non-negative integer is `{[k], {:type, :non_neg_integer}}`, every fault at once, and indexes that are no proper list `{[], {:type, :indexes}}`. It never raises (spec/00 §5 lists it among the readers). `row/2` reads a `:term` column, which a chunk holds as a list, from the chunk's start, so reading rows one at a time is quadratic in the chunk's rows; `rows_at/2` costs the same per row wherever it lies. `row/2` itself is unchanged. 50,000 rows × 9 columns, kernels loaded, median of 9 runs:

  | Read | All packed | One `:term` column |
  |---|---|---|
  | `row/2` over 1,000 ascending indexes | 450,553 r, 13.7 ms | 4,445,107 r, 33.3 ms |
  | `rows_at/2`, the same 1,000 | 95,584 r, 4.4 ms | 96,975 r, 7.9 ms |
  | `rows_at/2`, the same 1,000 shuffled | 139,971 r, 6.8 ms | 201,852 r, 8.2 ms |
  | `row/2` over every row | 22,501,767 r, 1,236 ms | 223,962,959 r, 2,284 ms |
  | `rows_at/2` over every row | 3,655,400 r, 277 ms | 3,555,351 r, 296 ms |
- **A gather of rows that repeat, in another order, reads each row it names** (#205, #226). The internal gather `Macaw.Data.Table.rows_at/2` is built on took a chunk's kept rows as a contiguous run when they spanned as many places as they held, which rows that repeat can do: `[10, 10, 12, 13]` read rows 10 to 13. No released path passed a repeated index (every caller's were distinct), so no answer of 0.14.0 changes.

- **Breaking: `Macaw.Data.Source.Finish.ceiling/2` refuses a budget that is neither `nil` nor a positive integer** (#199, #225, spec/01 §6.1). Its last clause answered whatever wasn't above the limit, so `ceiling(0, host: 10)` was `{:ok, {0, false}}`, `ceiling(-1, …)` and `ceiling(1.5, …)` answered themselves, and `ceiling(:nope, host: 10)` was `{:ok, {10, true}}`, an atom ordering above every number. Each is now `{:error, [{[:budget], {:type, :pos_integer}}]}`, answered with the `host:` and `page:` faults at once, the budget's first, and `ceiling!/2` raises it. A budget from `Macaw.Data.Source.Request.new/1` was already judged the same way, and no caller in the family is affected: macaw's surface fetch passes a budget macaw_component has already judged.

- **CI: the family's current `ci/raises.exs`** (#223). The family's raise check counts a raise inside a `__using__` or `__before_compile__` quote as compile time since 2026-11-09, so `mix hex.publish`'s check against the family reference refused 0.14.0 until it was published with the earlier copy. The new copy finds the same raise sites in `lib/`, every one allowlisted; `ci/` is not in the package.

## v0.14.0 (2026-11-10)
 (2026-11-10)

**macaw_layers 0.5.0, native kernels that answer their faults as terms, a push drain that costs the rows an increment brings, and a table whose kernel digest is its contents** (#101, #202, #204, #216, #218, #220). An adopter takes macaw_layers 0.5.0 with it, a few calls that raised now answer faults, `Macaw.Data.Native.elixir/1` and `normal_schedulers/1` run their function in a process of its own, and there is new public API, so this is a minor.

### Upgrading from 0.13.x

- **Take macaw_layers 0.5.0 too:** `{:macaw_layers, "~> 0.5.0"}`. 0.14.0 does not resolve against 0.4.x, and a project that calls macaw_layers itself takes that release's own changes. The move to 0.5.0 changes no digest by itself.
- **Calls that raised `ArgumentError` from the kernel now answer faults,** so a test rescuing it changes:
  - `Macaw.Data.Operations.step_digest/2`: `{:error, {path, :not_data}}` for a node holding a function, PID, reference, port or improper list; `Macaw.Data.Operations.Step.parts/4`, and so `Step.run/4` and `Macaw.Data.Operations.Cache.run/5`: `{:error, {key, :not_data}}`.
  - `Macaw.Data.Schema.from_json/2`, `Macaw.Data.Derived.from_json/2` and `Macaw.Data.Derived.from_map/2`: `limits:` that are no limits answer faults under `[:limits]`, such as `{[:limits, :depth], {:limit_value, 64}}`.
- **`Macaw.Data.Table.new/2` refuses an origin source or resolution that is not data,** `{[:origin, key], :not_data}`. It accepted one, and a sort or merge over the table raised later.
- **`Macaw.Data.Native.elixir/1` and `normal_schedulers/1` run their function in a process of their own.** The function must not use the caller's `self()`, mailbox or process dictionary (only `$callers` is carried): a `send(self(), …)` inside it reaches its own process, and a `receive` waits there. Its reductions are not the caller's, so a count taken around either call sees only the plumbing; take it inside the function. A raise, throw or exit reaches the caller as before. `Macaw.Data.Native.scope/2` answers `{:ok, result}` or `{:error, {:down, reason}}` instead of passing an exit on.
- **A kernel fault that is this library's defect raises `RuntimeError`,** naming the kernel, where an `ErlangError` such as `:ShortBuffer` was raised. Out of memory in a kernel is answered by the Elixir path. Nothing a caller passes reaches the raise, so only code rescuing `ErlangError` around a step changes.
- **Kernel digests of a term holding a table or a chunk move:** `Macaw.Layers.Document.digest/1` and `encode/1` follow `Macaw.Data.Table.equal?/2`, so equal tables chunked otherwise give one digest. A step identity whose `:term` option holds a table moves with them. Anything you stored keyed on such a digest is recomputed; `Macaw.Data.Table.digest/1` of a table with no table among its values, and every chunk digest, is unchanged.
- **New:** `Macaw.Data.Source.Push.cache/1`, `position/1` and `drained/1`; read them in place of the holder's struct fields. `Macaw.Data.Native.scope/2` and `scope!/2`.
- **`Macaw.Data.Source.Push.drain/2` answers what it answered** and costs the rows an increment brings: a 1,000-row increment into a nearly full open chunk 1,551,511 → 439,513 reductions (33.1 → 5.7 ms), and the first drain after a snapshot 10,266,302 → 785,865 (171.7 → 7.4 ms). Each kernel call costs 2 to 4 reductions more and `Macaw.Data.Table.Chunk.gather/5` 17 more; the tables are below.

### Changes

- **A native kernel answers a fault as a term, never as a Zig error** (#101, #208, spec/04 §1.7). Zigler turned a kernel's error return into an `ErlangError` through its error-return trace, whose debug-info globals it initializes on first use without a lock. A kernel now answers `{:fault, reason}` (`:short_buffer`, `:not_a_binary`, `:not_a_piece`, `:unknown_form`, `:out_of_memory`), and a compile-time check refuses one that returns an error union. Out of memory is answered by the Elixir path. Any other fault is a defect in this library's own packing and raises a `RuntimeError` naming the kernel and its arguments' shapes, where an `ErlangError` such as `:ShortBuffer` was raised before. The kernels' interface version is 8. Each kernel call counts 2 to 4 reductions more (a ladder partial over 8,192 rows: 39 → 42; the column sum: 215 → 219); its time is within noise.
- **A native kernel frees what it allocated when an allocation fails** (#101, #209, spec/04 §1.7). `group_sum` leaked its hash index when `Table.init`'s second allocation failed, found by extla's allocation model. Out of memory only, so no working call changes. Every kernel allocation now goes through one counted path, and the suite fails each allocation of each kernel in turn and finds nothing live at any return.
- **`Macaw.Data.Native.elixir/1` and `normal_schedulers/1` run their function in a process of their own** (#101, #210, spec/04 §1.7). Each put its flag in the caller's process and cleared it after the function, so a raise the caller caught left that process on the Elixir path, or on normal schedulers, for the rest of its life. Now the flag lives and ends with the function's own process, through the new `Native.scope/2` (`{:ok, result}` or `{:error, {:down, reason}}`) and `scope!/2`, which passes a raise, throw or exit on to the caller. The scopes nest. **Behaviour change:** the function's reductions are its own process's, not the caller's, so a caller counting reductions around either call counts only the call's plumbing; count inside the function's process instead. The function must not depend on the caller's mailbox or `self()`. The suite's `Macaw.Data.Test.Work.reductions/2` takes `native: :elixir | :normal_schedulers`, and its counts are 7 reductions lower than through the old scopes, which counted their own flag (a 2,000-row ladder partial: 18,879 → 18,872 on the Elixir path, 42 → 35 with the kernel).
- **New: `Macaw.Data.Source.Push.cache/1`, `position/1` and `drained/1`** (#202, #212, spec/01 §4), so a holder reads its subscription's schema cache, the number of the last message taken and how many snapshots and increments the last `drain/2` applied without the struct's fields. `drain/2` answers as before. New public API, so the next release is 0.14.0.
- **`Macaw.Data.Source.Push.drain/2` costs the rows an increment brings, not the rows already held** (#204, #213, spec/01 §1.1.4, §4). `Macaw.Data.Table.apply/2` wrote an open chunk again whole on every increment: every held row read, sorted and packed. Now only the increment is sorted, and rows starting at or after the chunk's last row are packed by themselves and joined after its columns as they lie, wherever the join is exactly what packing every row gives; any other chunk is written whole as before. The first drain after a snapshot folded the whole window column twice to find the served window's ends; it reads the column's positions instead, with the same answer. No answer changes: every chunk is byte for byte the one written before, digest and version included. `Macaw.Data.Test.LiveLoop`, a 1,000-row increment into the 50,000-row holding, kernels loaded, median of 11 drains:

  | Drain | Reductions | ms |
  |---|---|---|
  | open chunk nearly empty (56 rows) | 496,536 → 402,622 | 6.2 → 4.9 |
  | half (4,056) | 1,098,685 → 422,709 | 23.5 → 6.0 |
  | nearly full (7,056) | 1,551,511 → 439,513 | 33.1 → 5.7 |
  | first after the snapshot | 10,266,302 → 785,865 | 171.7 → 7.4 |
- **A late increment rewrites only the held rows after the first it moves** (#204, #214, spec/01 §1.1.4). The first held row later than the increment's earliest is found by binary search over the open chunk's packed window column; the rows before it are kept as they lie, and only those after it are read, merged with the increment and packed. A dictionary column now joins at any split, its kept rows' dictionary cut to the strings they hold. No answer changes. - **Depends on macaw_layers 0.5.0** (#216, #217, spec/00 §5), whose functions answer values where they raised; `{:macaw_layers, "~> 0.5.0"}`. Every digest is unchanged: each of the 18,985 distinct `Macaw.Layers.Document.digest/1` calls the 0.4.0 suite made answers the same bytes under 0.5.0, and no golden or stored digest moves. Where a call now answers a fault:
  - `Macaw.Data.Operations.step_digest/2` answers a node holding a term that is not data (a function, a PID, a reference, a port, an improper list) as `{:error, {path, :not_data}}`, its path in the node, and `Macaw.Data.Operations.Step.parts/4` (so `Step.run/4` and `Macaw.Data.Operations.Cache.run/5`) as `{:error, {key, :not_data}}`; each raised `ArgumentError` from the kernel. - **A table's digest uses the kernel's encoder, not a copy of it** (#218, #219, spec/01 §1.1.2). `Macaw.Data.Table.digest/1` encoded its header and every value no packed form holds with a byte-for-byte copy of the kernel's canonical encoder, kept while macaw_layers held it private; it now calls `Macaw.Layers.Document.encode/1`, so a change to the kernel's encoding moves table digests with `Macaw.Layers.Document.digest/1`'s. No digest moves: the 86,841 table digests the suite computed on 0.13.1's code (45,899 distinct, 2,574 integers beyond int64, 40,863 other terms and 28,867 zoned times among their values) replay identical, and no golden or stored digest changes. Two things follow from one encoder:
  - A struct in a column is encoded as the kernel encodes it, by its canonical term (`Macaw.Layers.Digest`, macaw_layers 0.5.0), where the copy encoded its map. No struct in this library or its family implemented the protocol then, so no digest moved (a table and a chunk do since #220, below); a caller's struct that does now has one digest however it is laid out. `Macaw.Data.Table.new/2` judges a struct by that canonical term too, so one whose canonical term is not data is `{[name, i], :not_data}`, never a raise when the table is hashed.
  - The copy's own `ArgumentError` is gone; a fault from the encoder over a term this library built is the one named invariant `ci/raises_allowlist.exs` already held.

  The kernel's encoder tracks a fault's path, so a value it encodes costs more: 4 reductions a big integer, 7 a small tuple or map. A zoned time column now encodes each of its zones once rather than a zone per value, from its packed zones, so it costs a quarter of what it did. - **The kernel's digest of a table is of its contents, not its layout** (#220, #221, spec/01 §1.1.2). `Macaw.Data.Table` and `Macaw.Data.Table.Chunk` implement `Macaw.Layers.Digest`, so `Macaw.Layers.Document.digest/1` and `encode/1` of any term holding one follow `Macaw.Data.Table.equal?/2`: the same rows chunked otherwise, compacted, sliced out of a longer table or held as a source's table give one digest, wherever the table sits in the term. They hashed the struct's fields before, so equal tables laid out differently got different digests, and a cache keyed on a term holding a table missed where it should have hit.
  - A table's canonical term is `{"macaw.table", [{name, type}, …], digests}`, the content digests of its rows `Macaw.Data.Table.chunk_rows/0` at a time: the digests a canonical table of the same rows keeps in its chunks. A table of whole canonical chunks reads them and hashes nothing, and fetches no cold chunk; any other layout hashes its rows a run at a time. A chunk's is `{"macaw.table.chunk", [{name, type}, …], digest}`, its content digest, never its id. A cold chunk, which held a function, now has a digest.

Nothing in this library or its family persists or compares such a digest across versions: its caches live in process memory, and a schema's version is over fields, which hold no table. The family's `lib/` digests no table (macaw's only kernel digest is a layout template's). Every other `Macaw.Data.Table.digest/1` and every chunk digest is unchanged: each of the 22,341 distinct `Macaw.Layers.Document.digest/1` and table-encoding calls the suite made on the previous code (18,816 and 3,525) replays identical, and none held a table.

## v0.13.0 (2026-11-05)

**Errors are values past the readers: every reader has a `!` twin, an improper list and arithmetic past a float's range answer faults, and `Macaw.Data.Reduce`, `Macaw.Data.FFT` and `Macaw.Data.Source`'s dispatch answer values** (#184, #169, #181, #185, #193, #192, #191, #195). A breaking change for a direct caller of `Macaw.Data.Reduce` or `Macaw.Data.FFT`, and new `!` twins.

### Upgrading from 0.12.x

- **Breaking: `Macaw.Data.Reduce.lttb/3`, `Macaw.Data.Reduce.m4/3`, `Macaw.Data.FFT.magnitudes/1` and `Macaw.Data.FFT.window/2` answer `{:ok, value}` or `{:error, reason}`.** Each answered a bare list. Call `lttb!/3`, `m4!/3`, `magnitudes!/1` or `window!/2` for the old answer. `lttb/2` and `m4/2` change with them. The `lttb` and `m4` steps keep the shape of their answers.
- **New `!` twins:** `Macaw.Data.Table.from!/2`, `Macaw.Data.Schema.from_map!/1`, `Macaw.Data.Schema.from_json!/2` and `Macaw.Data.Derived.from_map!/2`.
- **Calls that worked near a float's range are now refused,** with a fault in place of the answer. `8.0e307` is the bound called half the largest float below.
  - `Macaw.Data.Reduce.lttb/3`: `{:values, :overflow}` when `count × |x|`, `count × |y|` or `4 × x range × y range` reaches `8.0e307`.
  - `Macaw.Data.Reduce.m4/3`: `{:values, :overflow}` for an `x` at or above `8.0e307`, and `{:width, width}` for a width at or above it.

### Upgrading from 0.10.x

1. **`Macaw.Data.Window.position/1` answers integer Unix microseconds for every kind of time** (#127, #135). A `Date` was Gregorian days and a `NaiveDateTime` float Gregorian seconds; a `DateTime` was and is its Unix microseconds, and a number is itself. A caller that read a date's position as days or a naive time's as seconds divides by 86,400,000,000 or 1,000,000 (and shifts the epoch), or calls `Macaw.Data.Source.Order.instant/1` and converts.
2. **A `Date` or `NaiveDateTime` series under a budget may keep different rows** (#127). `"lttb"` and `"m4"` preselect on absolute power-of-two buckets, so the rescaled x moves the bucket edges. A series now keeps the same rows whichever kind of time it is given as, the rows a UTC series keeps, and the rows the `lttb` and `m4` transforms keep over the time column. An expectation or golden written from 0.10.0's reduction of a date or naive series changes; a `DateTime` or number series is unchanged. `:latest` now keeps the later of two naive times of one identity however close.
3. **A request window compares times of different kinds by instant, and `{:window, :mixed}` is gone** (#124, #134). A bound of another kind of time than the window field's values trims by instant where `Macaw.Data.Window.compare/2` raised `FunctionClauseError`, through `Macaw.Data.Source.Finish.finish/4`, the `Macaw.Data.Window` trims and `Macaw.Data.Derived.window/3`. `Macaw.Data.Window.check/2` no longer refuses a region range whose ends are different kinds of time, and `Macaw.Data.Source.Conformance` no longer calls such a served window malformed: drop any match on `{:window, :mixed}`, since only an inverted range is refused. A value with no reading on a bound's scale (a number or a string in a window of instants) lies in no window, as `nil` does. `Macaw.Data.Window.comparable?/2` is new.
4. **`min`, `max` and `extent` over a time column of mixed kinds answer a value** (#141, #143). `Macaw.Data.Operations.apply/4` raised `ArgumentError` and `Macaw.Data.Operations.aggregate/4` answered the fault `{["values"], {:reads, :comparable}}`. ## v0.10.0 (2026-11-02)

**Errors are values, a derived source reads columns, and a table is finished on its columns** (#114, #107, #105). A public function answers bad input with `{:error, reason}` and keeps its old return in a `!` twin; a CI guard holds `lib/` to it (spec/00 §5). A derived source may take its inputs as tables (`input: :columns`) and read them through `Macaw.Data.Derived.Columns`, which never makes a row. A derived source's output is a table, and the engine windows and finishes a table input on its columns. `filter` compares by the column's type, and `eq`/`ne` compare a time by its instant (#96, #102). This release is breaking for an adopter that calls any function whose return gained `{:ok, _}`, matches a derived output's rows, writes a derived source document that a 0.9.x reader must read, or relies on `filter` across kinds. The guide below lists what to change, and the entries after it give the detail.

### Upgrading from 0.9.x

1. **A function that answered its value now answers `{:ok, value}` or `{:error, reason}`** (#114, #117–#121). Where the input is known to be good, call the `!` twin, which keeps the 0.9.x return and raises `ArgumentError` in the module's `format_error/1` words. Otherwise match the result. The functions, each with its twin:
   - `Macaw.Data.Delivery`: `new/2`, `named_rows/1`.

   - `Macaw.Data.Derived.Functions`: `registry/1`.
   - `Macaw.Data.Operations`: `registry/1`, `step_digest/2`. `Macaw.Data.Operations.Step`: `run/4`, `parts/4`. `Macaw.Data.Operations.Cache`: `run/5` (`{:ok, table, cache}`).

A sum beyond a float's range is `:overflow` where it raised `ArithmeticError`.
2. **Implementers of the behaviors may answer faults.** A transform's `run/3` and `bind/3` may answer `{:error, {key, reason}}`, and an aggregate's `reduce/2` and `finish/2` may answer `{:error, :overflow}`. Code that calls these callbacks directly matches those answers.
3. **`filter` across kinds is a fault** (#96, #100, #102, #109, #118). An ordering (`lt`, `lte`, `gt`, `gte`) compares by the column's type, as `sort` does, and `eq`/`ne` on a time column compare by instant. A `value` that is no value of the column's type (a number against a time, a string against a number, an unparsable time, `nil` against an ordering) is refused once, before any row is read: `apply/4` answers `{[i, "value"], {:reading, type}}` and `apply!/4` raises it. In 0.9.x these answered silently by term order, so a time ordering kept the wrong rows; an expectation written from those rows changes. `filter(test: :eq, value: nil)` on a time column becomes `test: :absent`.
4. **A derived source's output is a table** (#47, #103, #104). `Macaw.Data.Derived.Engine.outputs/1` and `Macaw.Data.Derived.Engine.source/2,3`'s delivery carry a `Macaw.Data.Table`, so `Macaw.Data.Delivery.rows/1` of an output reads as any table's rows: every field present, `nil` where the function left one out, keys as strings, and a category's atom as its string (`%{"state" => "ok"}`, not `:ok`). Match an output's rows on those readings. Change is told by `Macaw.Data.Table.equal?/2`, so `1` → `1.0` now marks readers, while an atom and its string, or an absent field and `nil`, do not.
5. **`Macaw.Data.Derived.Engine.push/4` tells a changed delivery by value identity** (#106, #108). `1.0` re-delivered where `1` was is a change and recomputes; a table and the same rows as a list are two forms, so also a change. One table chunked two ways is not.
6. **`Macaw.Data.Derived.window/3` answers a table for a table input** under a request window (`window`, `box`, `region`, `latest`), where it answered the table's rows (#105, #125). Call `Macaw.Data.Table.rows/1` on it where you want rows; a list input still answers rows.
7. **Columnar derived sources: the form is version 2, and the kernels' interface is 7** (#107, #110–#113, #115).
   - `input: :rows | :columns` is new on `Macaw.Data.Derived`, `:rows` by default, so an existing source runs as before.
   - `to_map/1` and `to_json/1` stamp every derived source document version 2. A 0.10 reader reads a version 1 document, but **a 0.9.x reader refuses every 0.10 document** by name (`{:newer_schema, 2, 1}`). Upgrade every reader before a writer.
   - The native kernels' interface version is 7. A build with Zig recompiles them with the package; a library built for 0.9.x is refused at start and every step runs its Elixir path (with `native: :required`, the start fails), so rebuild the dependency (`mix deps.compile macaw_data --force`) if a stale build lingers.
   - A checker fault naming an allowed module's unknown function whose name is an accessor's names it by atom: `{:restricted, {Macaw.Data.Ops, :mean, 1}}`. `Macaw.Data.Derived.Sandbox.Allowlist.modules/0` lists nine modules.

## v0.8.0 (2026-10-31)

**The source contract is a time-varying relation, and a table is chunked** (macaw_data#10, #9), with **optional native kernels** (#38). A push is a numbered changelog of increments, retractions and range replacements, with settled ranges and derived watermarks. A table is a list of immutable chunks with stable ids, and every step runs a chunk at a time, through a caching contract a caller holds. Where Zig is in the build, the hot steps run natively, bit for bit as their Elixir path, and a 50k-row live frame meets visualize's ~17 ms budget. The suite's verdicts no longer depend on how loaded the host is. On macaw_layers `~> 0.3.0`, as 0.7.0 was. This release is breaking: the guide below is what an adopter of 0.7.0 changes, and the entries after it are the detail.

### Upgrading from 0.7.0

1. **A table is chunked, opaque, and equal by its contents** (#17). Compare tables with `Macaw.Data.Table.equal?/2`, never `==`, since the same rows chunked two ways are one value. Read a table through its functions (`rows/1`, `get/2`, `column/2`, `chunks/1`), never the struct's fields. `Table.t()` is opaque. Keep functions, PIDs, references and ports out of tables: `new/1` refuses them as `{[name, i], :not_data}`.
2. **Number a push's increments** (#12). A source sends `Push.increment_message/3`, numbered from 1 per subscription, and may send `Push.snapshot_message/2` with `served.position`. `Push.delivery_message/2` is gone. **Rows are no longer deduplicated**: an identical row pushed again is a second row. Guard redelivery by the number, not by the row.
3. **`Push.held/1`'s rows are a `Macaw.Data.Table`** (#19). Read held rows by name with `Macaw.Data.Table.get/2`, compare a category as a string, and expect a time column's values as `DateTime`s. Rows with no window value sort last.
4. **`sum` and `mean` are exact** (#21). Integers stay an integer. With a float among them, the exact sum is rounded once, ties to even, so a float sum may differ from a sequential sum in the last place: `[1.0e16, 1.0, -1.0e16]` sums to `1.0`, where it was `0.0`. A golden written from a sequential float sum may need regenerating.
5. **`lttb` is MinMaxLTTB, and `m4` and `lttb` reduce on one bucket ladder** (#22). `lttb` keeps at most `n` rows within its stated tolerance, the same under every chunking. The exact algorithm stays as `Macaw.Data.Reduce.lttb/3`. `m4` is exact over pixel columns whose edges move to a bucket edge, at most a quarter of a pixel. A time column reduces under the `:time` scale, in microseconds, by default; pass `scale: :linear` for the former seconds.
6. **The row helpers `Transforms.answer/4`, `point_reader/2` and `column/2` are gone** (#23). No table operation reads rows any more: a transform reads columns, or declares itself a column-native step (#20).
7. **Don't reuse a cache built by an earlier version.** An `Operations.Cache`'s `m4`/`lttb` partials changed shape twice (#40, #50), and `aggregate`, `sum`, `bin` and `spectrum` step keys no longer carry a chunk's place (#24). Drop a held cache on upgrade and let it rebuild.
8. **Native kernels are optional; nothing is needed to keep the Elixir path.** To build them, list `{:zigler, "~> 0.16.0", runtime: false}` in your deps and have Zig 0.16.0 in the build (#48). Zigler's `zig_doc` pins `ex_doc` to 0.39.1, so a project that lists `ex_doc` itself may need `override: true` on it. Without Zig the build prints a warning, not a compiler diagnostic, and every step runs its Elixir path, with the same results. Set `config :macaw_data, native: :required` to fail the build, and the start, without the kernels.

### Changes

- **Spec:** the source contract is one model, a relation that varies over time (#11, #10): a delivery is a snapshot, a push the changelog of Z-set increments, `Push.held/1` their integral, `:as_of` a past snapshot, a derived source a map from relations to relations (spec/01 §2.5). The deferred §2.6 and §4.1–§4.4, and spec/02 §8.6, specify what #12–#15 and macaw_data#9 build: numbered increments and the snapshot's handoff, retractions and range replacements, one resolution per subscription, settled ranges, and derived watermarks.
- **Breaking:** push increments are numbered, and a snapshot hands off to the stream by position (#12, spec/01 §4.1). A source sends `{:increment, seq, delivery}` (`Push.increment_message/3`, numbered from 1 per subscription) and may send `{:snapshot, delivery}` (`Push.snapshot_message/2`) whose `served.position` (new) is the last increment it reflects; `Push.delivery_message/2` is gone. `Push` drops a repeated or older increment whole (counted in `ignored`, a count by reason), applies increments in the order of their numbers, holds back those past a gap, records the gap and answers it from `Push.refetch/1`; a snapshot, received or fetched with the request's new `subscription:` and handed over by `Push.snapshot/2`, replaces what is held and drops the increments it already reflects. **Rows are no longer deduplicated:** an identical row pushed again is a second row (tally taps), so redelivery is guarded by the number, not the row. The conformance kit's `:push` check holds increments to their numbering. **Upgrade:** number each subscription's increments from 1 and send them with `increment_message/3`.
- **New:** pushed increments carry corrections (#13, spec/01 §4.2–§4.3). A delivery's `retracted` rows are withdrawn, each matched by identity, the window value it was held at and the fields it names, one copy per unit of weight, never a guessed row: one not held, held only at another window value, or that can't tell rows apart is `{:retract, reason, row}` in `errors`, and against a `capped` or reduced holding an unheld retraction is counted in `ignored` (`:unheld`). Its `replace` ranges, `%{from, to, identities, rows}`, make the relation over `[from, to)`, limited to identities, exactly the rows given; a change inside a replaced range, a replacement's row outside it and an overlapping replacement are recorded and not applied. Row retractions apply first, then range retractions, then insertions. An increment is merged only into a relation held at its `served.resolution`; a mismatch is recorded and answered by `Push.refetch/1`.
- **New:** settled ranges (#14, spec/01 §4.4). A delivery's `served.complete_until` is the source's watermark, a time or a number below which it expects no further change: settled, not final. `Push` carries the latest claim forward on what it holds and records a smaller one as `{:complete_until, :backwards, held, given}`, keeping the held claim; a new subscription starts afresh. A description may declare `lateness`, a hard bound (a `Duration` over a time window field, a number over a number one); given to `Push.new/3` as `lateness:`, it refuses a change older than the claim minus the bound (`{:late, row, bound}`) and a replacement reaching past it whole. Without it a change of any age is accepted.
- **New:** derived watermarks (#15, spec/02 §8.6). A derived source's output states `served.complete_until`, the minimum of its inputs' claims, each capped by its request window's upper bound; an input with no claim leaves none, and a change of the watermark alone marks the readers. A description may declare `idle_after` (milliseconds), which the owner passes to `Engine.new/2` by name (`idle_after:`): a source that has delivered nothing for that long, judged against the `now` the engine is given, is left out of the minimum until its next delivery, unless every input is idle.
- **Breaking:** a table is chunked, and its identity is its contents (#17, macaw_data#9, spec/01 §1.1.1–§1.1.2; an amendment to dco-tek/macaw/macaw#188 D5). A table is an ordered list of immutable chunks of `Macaw.Data.Table.chunk_rows/0` (8,192) rows, each column packed per chunk, so a column's form and a dictionary are a chunk's. `append/2`, `trim/2` and `slice/3` keep whole chunks and offsets into them, copying nothing, and `chunks/1` lists every chunk a table references. `Table.t()` is opaque. `equal?/2` compares contents strictly and `digest/1` is the content digest, the kernel's digest of the canonical term `{"macaw.table", [{name, type}, …], [values, …]}`. The same rows chunked two ways are one value, and `compact/1` rewrites any table into canonical chunks. Each chunk carries its own digest (`Table.Chunk.digest/1`), computed once when it is built. `new/1` refuses a value that is not data, a function, a PID, a reference, a port or an improper list, as `{[name, i], :not_data}`, since it has no digest. **Upgrade:** compare tables with `Macaw.Data.Table.equal?/2`, not `==`; read storage through `chunks/1`, never the struct's fields; keep PIDs, references and functions out of tables.
- **New:** chunk identity (#18, macaw_data#9, spec/01 §1.1.3). A chunk has a logical id, where it sits, and a version (`Chunk.id/1`, `Chunk.version/1`). A table built from rows names its chunks by their content digests. A source's table, built by `Macaw.Data.Table.new/2` with `origin: %{source, resolution, window, span}`, lays its chunks on fixed slots and names them `{source, resolution, slot}`: a span's start in event time, else a row offset that is a multiple of `chunk_rows/0`. So ids hold across a rebuild and a restart, and two resolutions never share one. `append/2` keeps a source's alignment, writing rows of the last slot into its chunk again, and `compact/1` keeps its slots. A description may declare `chunk_span`, and `Description.chunk_span/2` derives one from the resolution otherwise, never from the data. A step's output chunk (`Chunk.derive/3`, `Chunk.combine/3`, gathered by `Macaw.Data.Table.from_chunks/3`) is named after its inputs and step key. It is versioned by a derivation digest and its contents are not hashed, so a chain of steps hashes nothing.
- **Breaking:** `Push.held/1`'s rows are a chunked table (#19, macaw_data#9, spec/01 §1.1.4, §2.6). The rows are a `Macaw.Data.Table` of the source's origin, its columns the schema's fields, packed as `Delivery.table/2` packs them, so a category's atom reads back as its string and a time column's values as `DateTime`s. Every change reaches the table through the new `Macaw.Data.Table.apply/2`. It writes an open chunk's new contents and puts a settled chunk's changes (wholly before `complete_until`) in its delta: a deleted set, predicate deletes for replacements, and a side chunk of insertions, all applied on read. Lazy compaction at a quarter of the base keeps the chunk's id and digest and emits nothing. A cold chunk (`Table.Chunk.cold/5`) is never fetched for a predicate delete; its digest stays pending until `Macaw.Data.Table.warm/1`. `Push.new/3` takes `chunk_span:`. Rows with no window value now sort last in a source's table, as a push holds them. Rows that don't pack are `{:table, faults}` in `errors`. **Upgrade:** read held rows by name with `Macaw.Data.Table.get/2`, and compare a category as a string.
- **New:** steps run a chunk at a time (#20, macaw_data#9 §5, spec/04 §1.4). A transform may declare itself a column-native step: its class (`class/1`), the context it reads (`reads/0`), the context bound over the whole input (`bind/3`), the context as it resolves for a chunk (`resolve/3`) and the chunk's part (`chunk/3`); `Macaw.Data.Operations.Step` runs it, and `Step.parts/4` lists each chunk's view and step key, the step's identity, its context as resolved for the chunk and the run it reads, for a caller's cache. `filter`, `take` and `window` (without `latest`) are per-row steps: each chunk is passed through, dropped, cut to a run without copying, or gathered (`Table.Chunk.gather/5`, every column's slots copied, its id `{input id, step key}`), and the merge is concatenation. None of them transposes: at 50k rows `take n: 100` is about 0.01 ms (was 81 ms), `filter` about 8 ms (was 93 ms). `window` keys a chunk wholly inside it without `now`, drops one outside, and binary-searches a sorted window field (`Macaw.Data.Table.sorted/1`, a source's window field, kept by every per-row step) to cut only its edge chunks. `Macaw.Data.Table.from_chunks/3` takes views and `sorted:`; `Chunk.values/4` and `Chunk.at/3` read a step's column. `Macaw.Data.Table.from/2` names its columns without merging a row map. The row helpers moved to an internal module, Macaw.Data.Table.Edge, and are still called through `Macaw.Data.Table`.
- **New:** the associative combines (#21, macaw_data#9 §5, spec/04 §1.4, §1.2, §5). A step of class `:combine` declares `combine/3`, two runs' partials merged (associative, in chunk order), and `finish/3`, its table; `Step.merge/5` folds a table's partials and `Step.output/3` names a combine's output chunk over its inputs. `sum`, `aggregate` and `bin` (counting, or with `count`, `sum`, `mean`, `min`, `max` or `extent`) and `window` with `latest` are combines: any chunking and any grouping of their partials give equal tables. An aggregate may give the combining form, `merge/3`. **Breaking (values):** `sum` and `mean` sum exactly: integers stay an integer, and with a float among them the exact sum is rounded once to the nearest float (ties to even), so any order of the readings gives the same bits; a float sum may differ from the sequential sum in the last place (e.g. `[1.0e16, 1.0, -1.0e16]` sums to `1.0`, was `0.0`). `latest`'s ties are broken by chunk order, then row order, as before. Aggregates without the combining form (`median`, `quantile`, `distinct`, `variance`, `deviation`, `slope`, `delta`) still read every reading at once; a quantile stays exact, never a sketch.
- **Breaking:** `lttb` runs MinMaxLTTB, and `m4` and `lttb` reduce on one absolute bucket ladder (#22, macaw_data#9 §5, spec/04 §4.4, §4.5, §4.5.1). Buckets are `2^k` wide from origin 0 in the x scale's space, named by the new context keys `scale` (`:linear`, `:time` in microseconds, `:log` as `log2 x`; `:time` by default over a time column) and `level` (the previous level, for a hysteresis of a factor of 2). A chunk's partial depends only on its rows, the scale's kind and the level, so a zoom within a level reuses every partial, a zoom out folds finer partials (`Ladder.coarsen/2`), buckets straddling a chunk edge and gaps on one merge, and the count option leaves the step key (the new optional callback `keyed/1`). **`lttb`'s tolerance:** at most `n` rows without gaps, the first and last kept, deterministic, the same under every chunking; its mean interpolation error, over the y extent, is at most twice the exact algorithm's plus 0.005 (measured worst 1.27× sines, 1.37× walks, 1.56× sparse spikes). The exact algorithm stays as `Macaw.Data.Reduce.lttb/3`. **`m4`'s tolerance:** exact M4 over pixel columns whose boundaries move to a bucket edge, at most a quarter of a pixel away (half under hysteresis); `Reduce.m4/3`'s answer where bucket and pixel edges meet. A budget's reducer (spec/04 §7) picks as the steps do. A time column reduced under the default `:time` scale buckets in microseconds; pass `scale: :linear` for the former seconds.
- **New:** the global steps and the reshapes (#23, macaw_data#9 §5, spec/04 §1.4). A step of class `:global` gets every chunk's part in its `finish/3`: `sort`, `stack`, `spectrum`, and `aggregate` and `bin` with an `fn` that has no combining form (`median`, `quantile`, `distinct`, `variance`, `deviation`, `slope`, `delta`). A global output is one chunk named by its step key over its inputs' ids and versions, so a step after it still caches; rows kept across chunks are gathered by `Step.gather/5`, codes remapped. `fold` is a per-row reshape (`{:reshape, indexes, added}`, `Table.Chunk.reshape/7`: carried columns gathered with repeated indexes, the key and value added), and `stack` gathers across chunks with repeated indexes. `Stack.series/2` stacks data as given. No table operation calls `Macaw.Data.Table.rows/1` or `Operations.table/2` any more; the row helpers `Transforms.answer/4`, `point_reader/2` and `column/2` are gone.
- **New:** the caching contract (#24, macaw_data#9 §6, spec/04 §1.5, spec/01 §1.1.4). `Macaw.Data.Operations.Cache` is the example caller: a plain value the caller holds, keyed by `{Chunk.id/1, Chunk.version/1, step key}`. `Cache.run/5` reuses a held part, updates a changed chunk's part by inverse from its base's part where exact (`Step.update/4`, a step's new optional `update/4` and an aggregate's `retract/3`: counts, `bin` counts and integer sums), computes any other, and merges; its result equals `Step.run/4`'s. `Cache.prune/2` evicts by logical id. A lookup hashes nothing. A chunk with a delta keeps its base's version (`Chunk.base_version/1`) and a read view built once per state, so reads through a delta (`Chunk.values/4`, `Chunk.at/3`, a gather, `window`'s binary search) no longer apply the delta on every read, and compaction makes the view the base without repacking. **Fixed:** `aggregate`, `sum`, `bin` and `spectrum` no longer put the chunk's place (`:at`, `:rows`) in their step keys, so a chunk's key holds while other chunks come and go.
- **New:** parallel chunks on request (#25, macaw_data#9 §7, spec/04 §1.6, §3.2). `parallel: true` in the context asks `Step.run/4` (so every table operation through `Operations.apply/4`) and `Cache.run/5` to work a step's chunks across the schedulers, one task a part, when the input holds at least two chunks and `Step.parallel_rows/0` (16,384) rows; otherwise, and by default, they run inline. The parts reach the merge in chunk order whatever worked them, so a parallel run is bit-identical to the inline one, floating-point sums included. `parallel` is no step's declared context, so it never enters a step key.
- **Measurement:** a synthetic frame loop at 50k rows (#26, macaw_data#9 item 7, spec/04 §1.5): a live window with a chunk's worth of new readings a frame, running `take`, `filter`, `window` → `m4`, `window` → `lttb` and `sum` by series, recomputed in full and per chunk through `Operations.Cache`. The suite states the per-chunk cost in reductions (its changed chunks at most a full run over one chunk's readings, its frame at most half the full recompute); `mix test --only benchmark` prints the wall clock. Measured then, before #39–#54: about 400 ms a frame in full, 190 ms per chunk, of which about 95 ms is the `m4` and `lttb` merges. Results and the native-kernel decision are on macaw_data#9; #54 below gives the release's figures.
- **Faster:** `m4` and `lttb` merge their partials in work proportional to the chunks, not the buckets (#39, #40, spec/04 §4.5.1). A partial holds a piece per view, each run's buckets ascending, so `Ladder.combine/2` concatenates and reads no bucket; the chunk edges are joined once when the merged partial is read (`Ladder.runs/1`), and `finish/3` folds the buckets into pixel columns (`m4`) or takes its candidates in input order (`lttb`) in one pass. Results are unchanged under every chunking and grouping. In #26's frame loop the merges alone went from about 100 ms to about 40 ms a frame, and the per-chunk frame from about 215 ms to about 125 ms. A partial's term changed shape (`Ladder.partial/0`), so an `Operations.Cache` built by an earlier version is not to be reused.
- **Faster:** reading a column costs its slots, not its bits (#41, #42, spec/01 §1.1.5). An all-valid column decodes without expanding its validity bitmap; a slice cuts a bitmap as one little-endian integer; a gather takes an all-set bitmap without reading a bit; and `Chunk.gather/5` and `reshape/7` gather a run from the chunk's storage at its offset instead of slicing every column first. Bitmaps live in an internal module, Macaw.Data.Table.Bitmap. Results and digests unchanged.
- **Faster:** a chunk's `m4`/`lttb` partial is one pass with nothing allocated per row but new extremes (#41, #43, spec/04 §4.5.1). The bucket width is read once a partial, an integer x buckets by a shift (`s >>> k`, `s <<< -k`), a number x on a linear or time scale is read without a call, and the open bucket's first, last, least and greatest ride as loop arguments. About half the reductions a row; partials unchanged.
- **Faster:** grouping, exact sums and `filter` without per-row overhead (#41, #44, spec/04 §4.1, §4.10, §5). A chunk's groups are found in one pass, one map update a row, and grouping by one category column reads its dictionary codes and names each group once. `Exact` sums floats' signed mantissas by exponent and counts them in units of 2^-1074 once, when the value is read. `filter` scans a packed number column's buffer for an ordering against a number; **its passing rows, when they are one run, are now cut from the chunk without copying** rather than gathered (spec/04 §4.1), so such an output chunk is the input's, read from a row. Values unchanged.
- **Measurement:** the frame loop's pure-Elixir cost is pinned (#41, #45, spec/04 §1.5): a per-chunk frame at most 1,100,000 reductions (1,982,948 before #41) and its merges alone 600,000. spec/04 §1.5 states that a frame's garbage collection is the caller's to size: at the default heap a frame's wall time is mostly collecting the cache's partials, and the benchmark now also reports frames in a process whose minimum heap holds the cache (#46 takes up keeping partials off the heap).
- **New:** optional native kernels, built and loaded (#48, #38, macaw_data#9 §8, spec/04 §1.7). `Macaw.Data.Native` compiles Zig kernels through Zigler 0.16.0 when the build has Zig 0.16.0 (`.tool-versions`), found through `zig env`; Zigler is an optional dependency, so an adopter that wants the kernels lists `{:zigler, "~> 0.16.0", runtime: false}`. Without the toolchain the build prints a warning, not a compiler diagnostic, and every step runs its Elixir path. `Native.loaded?/0` is decided once at the application's start (the new application module, Macaw.Data.Application) and held in `:persistent_term`. `config :macaw_data, native: :optional | :required`, default `:optional`: `:required` fails the build without the toolchain, and the start when the kernels don't load. A call over at most `Native.sync_rows/0` rows (8,192, #49) runs on a normal scheduler, a larger one on a dirty CPU scheduler. Kernels are built ReleaseSafe, so a panic is never silent. CI tests with Zig under `:required`, without Zig, and checks that `:required` without Zig fails the build. `ex_doc` is now a dev and test dependency, pinned by Zigler's `zig_doc` to 0.39.1. #48 itself gives no step a kernel; #49–#53 below do. A kernel never replaces its step's Elixir path, which stays the reference, the path for every form a kernel hands back, and the whole of a build without Zig.
- **Faster:** a chunk's `m4`/`lttb` ladder partial runs in a native kernel where the kernels are loaded (#49, #38, spec/04 §4.5.2). `Ladder.partial/4` hands the view to it when x is int64, float64, a UTC, zoned or naive time or a date, and y is int64 or float64, on a linear or time scale; the kernel reads the packed buffers and validity bitmaps in place and answers the Elixir walk's piece term for term (`Ladder.partial_elixir/4`, the reference). Where the walk would answer past 64 bits or raise, it hands the view back. `Native.sync_rows/0` is 8,192, one canonical chunk: a call's time follows its answer's terms, at worst one bucket a row. Reductions count no kernel's work, so `Native.elixir/1` runs a function on the Elixir path (`Native.active?/0` false inside it), and the frame loop's reduction statements and pins are measured there.
- **Faster:** a ladder partial's piece is one packed binary, off the process heap (#50, #38, #46, spec/04 §4.5.3). The Elixir walk packs its segments (`Ladder.Packed`: a header with the points' number types, a fixed-width head a segment, 88 bytes a bucket; the external term format for a piece of mixed or past-int64 values), and the native kernel writes the same bytes rather than building a term a bucket. The frame loop's cache went from about 824,000 words on the caller's heap to about 11,000, so a collection no longer copies it; a test holds it under 50,000. `combine/2` still only concatenates; `runs/1` reads each piece once. Results unchanged. A partial's shape changed again (`Ladder.piece/0` is `{view, binary}`), so an `Operations.Cache` built by an earlier version is not to be reused.
- **Faster:** `m4`'s and `lttb`'s finishes run in native kernels where the kernels are loaded (#51, #38, spec/04 §4.5.4). `m4_finish` and `lttb_finish` read the merged partial's packed pieces in place, join them as `Ladder.runs/1` does, and answer the refs to gather: `m4`'s pixel columns, and `lttb`'s candidates through `Reduce.lttb/3`. Their arithmetic is Erlang's, operation for operation (exact integers, an integer converted to the nearest float where it meets one, strict floats), so the refs are the Elixir path's (`M4.refs/3`, `Lttb.refs/2`, held equal by a property test). A piece kept as a term, a value past int64 or anything Erlang would raise on is handed back to the Elixir path. A finish over at most `Native.finish_buckets/0` (2,048) buckets runs on a normal scheduler, a larger one dirty.
- **Faster:** the exact sum by group runs in a native kernel where the kernels are loaded (#52, #38, spec/04 §5.1). `sum`, and `aggregate` with `sum`, `mean` or `count`, over an int64 or float64 column grouped by one dictionary column or not at all, hand a chunk's view to `group_sum`, which reads the values, the codes and both bitmaps in place and answers each group's code, first row, rows, readings and exact-sum state (the internal Macaw.Data.Exact) (integers exact in 128 bits, past int64 as a bignum; floats' mantissas summed by biased exponent), so the part is the Elixir fold's term for term (held equal by a property test). A code past the dictionary or a non-finite float is handed back. A call answering more than `Native.sync_entries/0` (2,048) groups and exponent sums answers `:dirty` before building a term and runs on a dirty scheduler. Sum by series over an 8,192-row chunk: 127,254 → 173 reductions, ~2.3 ms → ~80 µs. kernels.zig is split by kernel family (buffers, ladder, finish, group).
- **Faster:** `filter`'s test and the gather of the rows it keeps run in native kernels where the kernels are loaded (#53, #38, spec/04 §4.1.1). `filter_mask` reads the tested column in place and answers the selection itself: `present`/`absent` from any column's validity bitmap, an int64 or float64 column against a number compared exactly as Erlang compares (an integer against a float past 2^53 too), a dictionary of strings by each string's answer decided once with the Elixir path's own test. `Column.gather/2` (every gather and reshape) copies fixed-width slots (`take`) and bitmap bits (`take_bits`) natively, the same bytes. Held equal to the Elixir path by property tests over every form, test and kind of value. `v > 0` over an 8,192-row chunk with rows apart: the mask 62,275 → 30 reductions (~470 → ~75 µs), the whole step 112,003 → 6,507 reductions (~1.2 → ~0.5 ms).
- **Measurement:** #26's frame loop with every native kernel (#54, #38, #9, spec/04 §1.5.1). Per chunk 958,680 → ~181,000 reductions and 36–47 → 7–10 ms at the default heap (13–16 → 6–8 ms with the frame heap sized); recomputed in full 1,931,845 → ~186,000 reductions, 55–58 → 9–11 ms. With the kernels the frame meets visualize's ~17 ms budget at the default heap, per chunk and in full. A new default-suite pin holds the frame with the kernels to at most 250,000 reductions per chunk, merges alone and in full.
- **New:** `Macaw.Data.Native.normal_schedulers/1` (#60, #61, spec/04 §1.7). It runs a function with every kernel call in its process on a normal scheduler, whatever the call's size. A call on a dirty scheduler is charged reductions by its time, about four a microsecond, so a count with one in it moves with the host's load. A normal-scheduler call is charged a fixed few. Use it for a statement of work in reductions with the kernels, such as the frame's (spec/04 §1.5.1), never for serving: a large call then holds its scheduler past the 1 ms rule. `scheduler/1`, `finish_scheduler/1` and the new `entry_limit/0` answer for it.
- **Fixed:** a bounded call is hung only when it is blocked (#33, #62, #67, spec/02 §6.4, spec/01 §9). The conformance kit's runner and the derived engine's sandbox called any call still running at `timeout` hung, so on a loaded host a slow compile or a capped CPU-bound call was misjudged `{:hung, …}`. Now a call with a reductions cap is judged by its count while it works. It is hung only once it has been waiting in `receive`, its reductions unchanged, for `timeout` ms on end, and each piece of work gives it the whole bound again. A call with no cap still has only the clock. A wait on another process is a block all the same, so give a stored function a generous `timeout:`, as spec/02 §6.4 asks.
- **Fixed:** the first stored function no longer waits on the code server (#69, spec/02 §6.3). In interactive mode a node's first compile loads Elixir's own modules on first use, and a busy code server could hold a bounded compile past its timeout. The application now compiles and runs one trivial function through the sandbox as it starts, so those modules are loaded before any bounded compile. Starting the application costs that one compile.
- **Docs:** spec/00 names the dependencies as they are, with no pinned version: `macaw_layers` required, and `table`, `nx` and `zigler` optional (#34, #70). Every doc reference resolves, and CI builds the docs with `--warnings-as-errors`.

## v0.7.0 (2026-10-30)

**Terms are the form** (dco-tek/macaw/macaw#188), macaw_data's part. A value's identity and validity are the BEAM term's own; JSON and Arrow are adapters at the edge. On macaw_layers 0.3.0. This release is breaking throughout; the guide below is what an adopter of 0.6.1 changes, and the entries after it are the detail.

### Upgrading from 0.6.1

1. **Depend on macaw_layers `~> 0.3.0`** (#27); its own upgrade guide applies to any kernel call you make directly.
2. **Every schema version changes** (D1). A stored version, cache key or golden written by 0.6.1 differs; regenerate it. A schema's names, states and roles are now strings in the struct (`Schema.new/1` normalizes them), so code that pattern-matches `:latency` inside a schema matches `"latency"`; every function that takes a name still takes either spelling.
3. **A data color is a color term** (D2): a `%Macaw.Layers.Color{}` literal or a typed color, never a string. Parse CSS text at your input edge with `Macaw.Layers.Color.parse!/1`, or write `~RGB"#3b6fa8"` in code. A role spelled like a CSS name (`"orange"`) is now a valid status role.
4. **A derived source is built from its value** (D3). Pass `Derived.new/1` a keyword list or a map of terms; read a stored form with `Derived.from_map/2` or `from_json/2`. `to_map/1` and `to_json/1` now answer `{:ok, form}` or faults.
5. **The operations registry's digest changes** (D4); a compile cache keyed by it recompiles once. `Operations.step_digest/2` is new: a checked step's canonical identity.
6. **Category values read back as strings** (D5): a `:category` column holding `:ok` answers `"ok"` from `rows/1`, `get/2` and `column/2`; compare with strings, or with `Operations.same?/2`. `nil`, `true` and `false` are kept.
7. **Packed columns are faithful and Arrow-compatible** (D5). A mixed integer/float column and a zoned time read back exactly as given; anything that held packed buffers (stored binaries) changes with the bitmap order.

### Changes

- **Breaking:** on macaw_layers `~> 0.3.0` (#27): the kernel's digest is over the value, so every pinned version moved before D1 changed what it digests.
- **Breaking:** every schema version changes (D1, #28, dco-tek/macaw/macaw#188). `Schema.version` is the kernel's digest of the schema's term, not of its JSON form, which is now only an adapter at the edge; a value entry's color no longer goes through the JSON form when `Schema.new/1` versions the schema, so a typed color there can't crash it. The struct holds every field name, state and role as its string, normalized once by `new/1`, so `fields`, `identity/1`, `window_field/1`, `compatibility/2`'s faults and `identity/2`'s maps name fields by their strings; every function that takes a name still takes either spelling. A state named in both spellings in one description is `:duplicate`.
- **Breaking:** data colors are color terms, and a string is never a color (D2, #29, dco-tek/macaw/macaw#187, dco-tek/macaw/macaw#188). A value entry's `color`, a `:color` field's row values (a derived source's output), a `:color` parameter and `Schema.color?/1` take a literal `%Macaw.Layers.Color{}` or a theme-relative typed color (`{:color, "good"}`, `{:alpha, {:color, "bad"}, 0.74}`), its names in a theme's name grammar; a string there, `"#2e7d32"` or `"red"`, is `{:type, :color}`. `new/1` holds a typed color's names as strings, so `{:color, :good}` and `{:color, "good"}` are one version. The schema's JSON form writes and reads an entry's color in macaw_layers' color form (`Macaw.Layers.Color.Form`: `{"$rgb": "#2e7d32"}`, `{"$color": "good"}`), making no atom. `Macaw.Data.Table.column_types/1` infers `:color` for a column of color terms; a column of strings stays `:text`. A status role spelled like a CSS name (`:orange`) is now a role. **Upgrade:** read CSS text into a color at your input edge with `Macaw.Layers.Color.parse!/1`, or write `~RGB"#2e7d32"` in source (`import Macaw.Layers.Color, only: [sigil_RGB: 2]`); a stored schema whose entry colors are strings reads back refused, so convert its colors with `parse!/1` before reading it.
- **Breaking:** a derived source is built from its value, and its forms are an adapter (D3, #30, dco-tek/macaw/macaw#188). `Derived.new/1` takes the value only, a keyword list or a map of its fields as terms; it no longer guesses whether it was given a map form, and a map form's string keys are each `:unknown_key`. The map and JSON forms are written and read by macaw_layers' JSON adapter (`Macaw.Layers.Form`), with the kernel's tags and the source's own in one tag table: `to_map/1` and `to_json/1` answer `{:ok, form}` or every value without a form, by path; `from_map/2` and `from_json/2` read through the gates (the limits, the version, the tag table, the keys, making no atom) and then judge the value with `new/1`. The output schema is used as built, a `%Schema{}` as given and fields by `Schema.new/1`, never written to its form and read back; in the form it is `Schema.to_map/1`'s. `Derived.Form`'s private tag scheme is gone. A color, literal or typed, in a schema's value entry reaches a stored function's context as the term it is; before, its tags were respelled as strings. **Upgrade:** the form changed: an input is `{"$input": [name, window]}`, a source's name `{"$source": name}`, `per` `{"$atom": "identity"}` or `{"$identity": input}`, a region an object keyed by field names, and `to_json/1` stamps `"$version": 1`. Nothing in this library stored the old form of pair lists, so no version step reads it: write a stored source again with `to_map/1` from its value. Read a map form with `from_map/2`, not `new/1`.
- **Breaking:** the operations registry's `digest/1` is the kernel's term digest of its names and modules, not a SHA-256 of `term_to_binary` (D4, #31, dco-tek/macaw/macaw#188), so every registry digest changes and a compile cache keyed by one recompiles once. New: `Operations.step_digest/2`, a checked step's canonical identity, for caches of a step's results.
- **Breaking:** a table's packed columns are faithful and laid out as Arrow lays them out (D5, #16, dco-tek/macaw/macaw#188), spec/01 §1.1. Packing never changes a value. A category column of strings and atoms is one Arrow dictionary of strings, so `rows/1`, `get/2` and `column/2` read a category's atom back as the **string** that spells it (`:ok` and `"ok"` are one code, read as `"ok"`), in every form the column takes; `nil`, `true` and `false` stay themselves, beside the names in side bitmaps, so `[:ok, true, "warn"]` reads back `["ok", true, "warn"]`. Validity bitmaps are least-significant-bit first, Arrow's order, not Elixir's `<<b::1>>` order, so every stored packed binary changes. A `DateTime` keeps its zone (name, abbreviation and both offsets, in a per-column dictionary, with no time-zone database) and its precision, so a time reads back as given rather than in UTC at microsecond precision. A text column is an offsets buffer and one data buffer, Arrow `utf8` when every value is valid UTF-8 and Arrow `binary` when one is not; a category column holding a string that is not valid UTF-8 is kept as its list. `new/1` takes `NaiveDateTime`s and `Date`s in a time column as themselves, and refuses a value in a `:color` column that is not a color term (`Schema.color?/1`), `{[name, i], {:type, :color}}`. **Upgrade:** compare a category value with `Operations.same?/2`, or as a string.
- **Fixed:** a number column mixing integers and floats reads back each as given, through an integral bitmap, or a dense union of int64 and float64 when an integer is beyond ±2^53; an integer beyond int64 keeps its column a list rather than becoming a float. A time column keeps each value's zone and precision, so `~U[2026-01-01 00:00:00Z]` and `~U[2026-01-01 00:00:00.000000Z]` stay distinct (#16, dco-tek/macaw/macaw#188).
